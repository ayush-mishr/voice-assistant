# Audio Streaming Architecture & Full Flow Guide

This document explains the complete end-to-end audio streaming architecture, code flow, and the logic implemented to achieve real-time, low-latency voice interaction within the application. The system connects a web-based microphone interface to an AWS Bedrock (`amazon.nova-sonic-v1:0`) language model, augmenting it with RAG capabilities through a dual-memory system.

---

## 1. High-Level Flow 🌐

The architecture acts as a real-time, bi-directional bridge between the user's browser, the application back-end, and the Nova Sonic Voice LLM.

1. **Audio Capture**: The frontend accesses the microphone, chunks the audio, and converts the feed into 16kHz Int16 PCM chunks.
2. **WebSocket Transport**: The browser sends these PCM binary chunks directly via WebSocket (`/ws`) to the backend server.
3. **Backend Agent (FastAPI)**: The server intercepts the voice traffic, retrieves context through the **Agent Core**, generates an augmented prompt (RAG context), and forwards the stream to AWS Bedrock.
4. **LLM Generation**: AWS Bedrock generates a real-time spoken response and streams chunks of 24kHz Int16 PCM audio back.
5. **WebSocket Transport**: The server relays these response binary chunks to the frontend.
6. **Playback Engine**: The frontend uses a pull-based AudioWorklet engine to buffer and play the audio seamlessly, with native protection against audio stutter.

---

## 2. Frontend: Audio Capture (`useAudioCapture.js`) 🎤

The file `frontend/src/hooks/useAudioCapture.js` oversees capturing user audio with low latency and converting it for AI processing.

### **Steps:**
- Uses the `navigator.mediaDevices.getUserMedia()` API configured with Echo Cancellation and Noise Suppression (sampleRate: `16000`, single channel).
- Creates an `AudioContext` and registers a custom `AudioWorkletProcessor` called `PCMProcessor`.
- **Chunking algorithm:**
  The `PCMProcessor` takes native `Float32` frames from the microphone in chunks of 4096 samples. It immediately converts these arrays into `Int16Array`, which maps to the 16-bit PCM expected by AWS (`s < 0 ? s * 0x8000 : s * 0x7FFF`).
- Once a chunk reaches 4096 items, it is posted as an `ArrayBuffer` directly to the main thread via `postMessage`.
- The main thread then calls `onPCMData`, which passes the ArrayBuffer directly to the WebSocket.

---

## 3. Communication: WebSocket Layer (`useWebSocket.js`) 🖧

The file `frontend/src/hooks/useWebSocket.js` acts as the bi-directional nerve center for UI components and stream processing.

### **Steps:**
- It establishes a WebSocket connection (`ws://<host>/ws`) with `binaryType = 'arraybuffer'`.
- **Outgoing:**
  Uses `sendBinary(ArrayBuffer)` to send the raw mic chunks generated by `useAudioCapture`, and `sendJSON(object)` to push configuration messages and context payload triggers.
- **Incoming:**
  Listens actively to the `ws.onmessage` event:
  - If `event.data` is an `ArrayBuffer`, it passes it heavily straight to `useAudioPlayback.js` (`onAudio({ chunk })`).
  - If `event.data` is a JSON string string, it dictates application state updates (like `processing`, `speaking`, `transcript` events). 
- Implements auto-reconnect with a 3-second debounce to ensure session stability.

---

## 4. Backend: WebSocket Bridge & Agent Core (`server.py` & `agent_core.py`) 🧠

`backend/server.py` and `backend/agent_core.py` handle the bidirectional stream orchestration combined with the LLM reasoning loop.

### **Steps:**
1. **Connection Intake (`server.py`)** 
   - A single FastAPI endpoint (`/ws`) mounts an active connection.
   - The stream passes settings specific to Amazon Nova, asserting incoming encoding (`16000Hz lpcm`) and targeting output audio config (`24000Hz lpcm` returning from Bedrock).
2. **Context & RAG Compilation (`agent_core.py`)**
   - The user query hits the Agent Core Orchestrator.
   - The Short-Term Context Cache (TF-IDF cache) is evaluated. If present, it skips long processing.
   - On cache miss, Long-Term Memory (FAISS Vector Store with document embeddings) generates semantic search matching chunks.
   - A newly augmented `RAG_SYSTEM_PROMPT` is compiled, forcefully instructing the model to constrain its responses using ONLY the indexed retrieved context (meaning the user interacts with localized data, not just standard cloud inferences).
3. **Piping to Bedrock (`InvokeModelWithBidirectionalStream`)**
   - Incoming WebSocket binary payload chunks are transformed into AWS `BidirectionalInputPayloadPart` bytes in background `asyncio` tasks. AWS Bedrock begins immediately streaming output frames natively.
   - The backend loops continually over Bedrock's asynchronous stream response logic and pushes them directly out via `await websocket.send_bytes(...)`.

---

## 5. Frontend: Audio Playback & Jitter Management (`useAudioPlayback.js`) 🔊

The backend loop can be inherently bursty and prone to jitter, especially in asyncio loops. Trying to schedule those chunks via native Nodes inevitably produces stutters and gaps. `frontend/src/hooks/useAudioPlayback.js` resolves this using an ingenious **Pull-Based AudioWorklet**.

### **Steps:**
- **Translation:** Receives an Int16Array chunk from WebSocket, converting it back to Float32 sample format (by simply dividing by `32768.0`) natively required by browser Audio APIs.
- **Queueing Structure:**
  The Float32 `ArrayBuffer` items are piped directly inside an inline `AudioWorkletProcessor` component called `PlaybackProcessor`. Here, they reside inside an internal FIFO (`_chunks` buffer).
- **The PULL Model:**
  The process uses a **Prebuffering Threshold**. It waits deliberately (`~120ms` lead buffer / approx `1200` samples) before allowing any sound to emit. Once filled, the processor independently "pulls" samples recursively matching the OS driver output.
- **Anti-Stutter Adaptive Algorithm:** 
  If network jitter interrupts the relay and the FIFO experiences an "Underrun", the component actively pads output frames with zeroes (silence) temporarily. Crucially, it then dynamically bumps up the needed pre-buffer parameter (e.g. `prebufferSamples += 240`). 
  This means under rough networking circumstances, latency imperceptibly increases to save fluid voice, while under perfect connection the playback stays gaplessly real-time.

## Architecture Flow Recap Chart

\`\`\`
[USER] -> Speaks to Microphone
       🔽   (useAudioCapture)
       | -> Chunked into 4096 size frames -> Float32 -> Int16
       🔽
[FRONTEND WEBSOCKET]
       | -> Translates frame via `sendBinary()` over ArrayBuffers
       🔽   (useWebSocket)
[FASTAPI SERVER /ws] 
       | -> Reads Stream
       | -> Agent Core queries Long-Term (FAISS) + Short-Term (TF-IDF) 
       | -> Assembles RAG Augmented System Prompt
       🔽
[AWS BEDROCK (amazon.nova-sonic-v1:0)]
       | -> Consumes input stream asynchronously & evaluates contextual prompt
       | -> Originates generated verbal Int16 lpcm bytes stream
       🔽
[FASTAPI SERVER]
       | -> Streams generated bedroock partial payloads down websocket over binary frames
       🔽
[FRONTEND WEBSOCKET]
       | -> Emits onAudio(binary byte chunk)
       🔽   (useAudioPlayback)
[AUDIO ENGINE WORKLET]
       | -> Converts back to Float32
       | -> Stores in FIFO Buffer. Analyzes prebuffer length. 
       | -> Engine "Pulls" gaplessly at 24kHz -> Plays uninterrupted output.
\`\`\`
